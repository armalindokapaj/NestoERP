# Form manifest (AUD-09 §2, FV-01)

Every existing tenant and Platform Admin business editor in NESTO, as the code stands: RecordForm pages, FormDialog configurations, custom forms, inline editors and upload controls. For each one it records the input schema the server parses, required fields and defaults, dependent and conditional fields, how values are serialised (omit / clear / preserve, and what happens to hidden fields), the fields the server owns, the submit adapter, conflict handling, uploads, drafts and the tests that cover it.

It is an inventory of what exists, not a design. An absent feature (no draft, no version token) is recorded as absent, not invented (PRD §2).

## How this file is kept honest

`tests/unit/forms/form-manifest.test.ts` scans `components/**` and `app/**` (except `components/3d` and `app/(experience-editor)`) for files that render `<RecordForm`, `<FormDialog`, or a `<form>` with `onSubmit`/`action`, and fails if one of them is not named here in backticks, or if a file named here no longer exists. It also holds every table row to the 13 columns below. Adding, moving or deleting a form means adding, moving or deleting its row.

Inline editors with no `<form>` (values saved from buttons, menus, grids or autosave through `useValuesEditor`, `useEditorSave` or `useUnsavedEditor`) are listed too, although the scan cannot find them for you. They are marked "inline editor".

## Vocabulary

- **Adapter families.**
  - *RecordForm*: `components/forms/record-form.tsx`. Posts FormData to a server action that returns an outcome; AUD-03 navigates by the returned `redirectTo`.
  - *FormDialog*: `components/engineering/form-kit.tsx`, a configured dialog. `payloadFor` builds JSON from field configs, then `engineeringApi` calls a route. `components/sales/unit-sales/unit-sales-dialogs.tsx` carries a second `FormDialog` of its own.
  - *custom*: a hand-written form that submits JSON to a route or calls a server action directly.
  - *inline editor*: saves without a form.
- **Serialization terms.**
  - *omit*: the key is not sent, so the server keeps the saved value.
  - *clear*: an explicit `null`, `""` or `false` is sent, so the server erases the value.
  - *preserve*: the stored value is re-sent unchanged.
  - *Hidden-field policy*: what a field that is hidden, disabled or permission-withheld sends.
- **Server-owned.** Fields the server derives or revalidates whatever the client sends: company, actor, numbers, totals, status, timestamps.
- **Conflict handling.**
  - *expectedVersion* / *version token*: an optimistic concurrency check.
  - *AUD-02 conflict review*: the task conflict flow.
  - *P2002→CONFLICT*: a uniqueness violation mapped to a business conflict.
  - *none*: the last write wins.

## Upload controls (AUD-09 §8, FV-18, FV-19)

Every upload in the product runs through the Documents pipeline. The browser half is `components/documents/upload-client.ts`; the queue is `components/documents/upload-queue.tsx`. The server half is `lib/modules/documents/storage/upload.service.ts`. The server verifies the owner, the parent's scope, the size (by HEAD), the type (magic bytes, never the extension or the browser MIME alone) and the scan policy. One chosen file is one upload key for all of its retries.
